2. La solución y su arquitectura

La app es una votación en vivo: se crea una encuesta, la pantalla muestra un QR, el público vota desde el celular y las barras se refrescan cada 2 segundos. Reglas que se prueban: un voto por votante, encuesta cerrada, opción inexistente, porcentajes que suman 100. Los votos viven en DynamoDB, así que un deploy o un rollback no los borra.

Si el smoke pasa: publish-releaseRelease v1.0.N con notas automáticas y aviso a Discord
Si falla el deploy o el smoke: rollbackfind-rollback-release, rollback-production (ambiente production-rollback, sin revisores), smoke-test-rollback y notify-rollback. El run termina en rojo a propósito

Particularidades

ParticularidadDetalle
EventosPR a main: solo build-and-test. Push a main: todo el flujo, salvo cambios que solo tocan **.md, docs/**, sustentacion/** o pages.yml (paths-ignore). workflow_dispatch para correrlo a mano.
Un solo deploydeploy.yml (workflow_call) lo usan staging, producción, el rollback automático y el botón de pánico. El camino para volver es el mismo que se probó para ir.
VersiónVERSION trae 1.0; el PATCH es github.run_number. Etiquetas 1.0.N y SHA completo.
Rollback sin aprobaciónEl regreso usa el ambiente production-rollback, sin revisores. Si usara production, esperaría a una persona.
Releases como puntos de restauraciónLa Release se crea solo después del smoke de producción. Por eso, si una versión falla, la última Release es la última versión buena.
Concurrenciaconcurrency sin cancelar: un terraform apply nunca se corta a la mitad.
Calidad que no bloqueaFlake8 y Pylint corren con --exit-zero y sus reportes los lee SonarCloud. Black, ESLint, gitleaks, Trivy (CVE críticos con corrección), cobertura y quality gate sí bloquean.

6. Decisiones que se apartan de la guía o del plan

DecisiónPor qué
Equipo de 2, no de 3Autorizado por el profesor. Los roles se reparten entre Sergio y Valeria.
AWS personal de Sergio, no Learner LabCuesta dinero real mientras los dos ambientes estén encendidos. Usa llaves permanentes de un usuario IAM de CI (sin AWS_SESSION_TOKEN) y hay que destruir todo al terminar.
LabRole creado a manoEl Learner Lab lo trae. Se creó igual para que infra/main.tf lo lea con un data source: confianza ecs-tasks, AmazonECSTaskExecutionRolePolicy y AmazonDynamoDBFullAccess.
Rollback con ambiente propioEl ambiente production-rollback no tiene revisores, para no esperar aprobación al volver.
Rollback de la imagen, no de la infraUn cambio malo de Terraform se corrige con git revert y el pipeline normal.
HTTP sin TLSComo en el Taller 3. Selenium usa --disable-features=HttpsFirstBalancedModeAutoEnable porque Chrome 157 deja en blanco los sitios solo HTTP.
Llaves permanentes en GitHub Secrets, no OIDCEs lo que ya funcionó en el Taller 3 y es lo más corto de montar. Son las llaves del usuario IAM github-cicd-votaciones. OIDC sería lo ideal.
El rol admin puede saltarse proteger-mainEl ruleset exige PR con 1 aprobación y el check build-and-test, y bloquea borrar la rama y el force push, pero el rol admin puede saltarlo. Valeria aún no aceptó la invitación, así que no hay segunda aprobadora.

9. Por qué importa cada parte

  • Staging antes de producción: en el Taller 3 el fallo de Selenium apareció en staging y producción no se tocó. Aquí pasa lo mismo con el E2E.
  • Una imagen por versión: lo que se prueba en staging es lo que llega a producción, sin reconstruir.
  • Releases: son la lista de versiones buenas. Sin una Release previa el rollback no sabe a dónde volver.
  • DynamoDB fuera del contenedor: los votos sobreviven a un deploy o a un rollback, y el esquema no cambia entre versiones.
  • Aprobación manual: convierte el despliegue continuo en entrega continua; el equipo decide el momento en la demo.
  • gitleaks y Trivy: una llave filtrada o un CVE crítico detiene el pipeline antes de publicar la imagen.
